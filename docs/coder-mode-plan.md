# План внедрения кодер-режима в ZVS Assistant

Дата: 24.08.2026
Статус: план, код не пишется
Базовая ревизия: `desktop/` (Electron + React/MobX + better-sqlite3 + AI SDK v7), `crates/tools` (Rust napi)

---

## 0. Резюме

Ассистент уже содержит бо́льшую часть инфраструктуры, нужной кодер-агенту: агенты с политиками, реестр инструментов, исполнение команд с одобрениями, скиллы, память, векторные хранилища, движок сценариев, секреты. Не хватает четырёх вещей, и три из них — не те, что в исходном списке.

Критично отсутствуют:

1. **Файловые инструменты.** Агент умеет `cmd_exec` (PowerShell), `grep_search`, `regexp_search` — и всё. Нет чтения, записи, точечного редактирования, применения патчей, диффов, отката. Кодер-агент на одном PowerShell — это агент, который «пишет» код через `Set-Content` вслепую.
2. **Полноценный журнал сообщений.** В `RunEngine.execute` история собирается так:
   ```ts
   role: m.role === "tool" ? "assistant" : m.role,
   content: m.text
   ```
   То есть tool-вызовы и их результаты в контекст **не попадают вообще**. Модель на шаге N+1 не видит, что вернул инструмент на шаге N. Для чата это терпимо, для кодера — фатально.
3. **Учёт токенов.** Поля `generation_runs.input_tokens/output_tokens` в схеме есть, но всегда `0` — usage из `streamText` нигде не читается. Без этого невозможен ни триггер компактирования, ни `/cost`, ни выбор модели по остатку лимита.
4. **Обрезка контекста вместо управления им.** `HISTORY_MAX_MESSAGES = 80`, `HISTORY_MAX_CHARACTERS = 60_000` — старое просто исчезает без следа.

Отсюда порядок работ: сначала фундамент (журнал + токены), затем файловые инструменты, и только потом компактирование, хот-свитчинг, проекты и CLI. Компактировать нечего, пока в контексте нет tool-результатов; переключать модели без потери контекста невозможно, пока контекст не пересобирается из журнала детерминированно.

## 2. Целевая архитектура

### 2.1 Ключевое решение: единое ядро, две оболочки

```
packages/
  core/           @zvs/core — чистый TypeScript, без electron
    domain/       модели, zod-DTO, инварианты
    context/      журнал, токенизация, бюджет, компактирование
    runtime/      RunEngine, tool loop, ModelChain, ResilientModel
    tools/        реестр + реализации, порты наружу
    persistence/  репозитории (better-sqlite3)
    policy/       directory/terminal/approval, наследование
  desktop/        Electron: IPC, окна, трей, React UI  → зависит от core
  cli/            zvs: headless + TUI                  → зависит от core
crates/
  tools/          Rust napi: поиск, обход, токенизация, применение ханков
```

Ядро общается с внешним миром через порты (`FileSystemPort`, `ProcessPort`, `SecretsPort`, `ClockPort`, `ApprovalPort`). Оболочки поставляют реализации. Так CLI получает ровно ту же логику и те же политики безопасности, что и GUI.

**Про Rust.** Рекомендация: держать в `crates/` производительные примитивы (поиск, watcher, токенизатор, применение unified diff, хэширование дерева репозитория) и вызывать их из TS через napi — как уже сделано с `search.rs`. Писать второе, независимое ядро на Rust — не рекомендую: доменная логика завязана на AI SDK (TypeScript), а дублирование инвариантов политик даст расхождение реализаций, то есть дыры в безопасности именно в том месте, где агенту разрешают писать в файловую систему.

### 2.2 Ключевое решение: журнал вместо истории

Вводится понятие **Run Journal** — упорядоченный, полный, неизменяемый журнал событий диалога. Из него **детерминированно собирается** массив `ModelMessage` под конкретную модель на конкретном шаге.

```
Journal (БД, полный)  ──[ContextBuilder(model, budget)]──▶  ModelMessage[] (эфемерный)
```

Следствия, ради которых это делается:

- Компактирование становится **представлением**, а не разрушением: сжали — исходники на месте.
- Хот-свитчинг становится тривиальным: сменили модель — пересобрали контекст под её лимит и её возможности.
- Микро-компактирование (пересборка перед каждым шагом) устраняет накопление мусора внутри одного рана.
- Появляется воспроизводимость: контекст любого шага можно восстановить и продиагностировать.

Хранение: `chat_messages.content_json` расширяется до дискриминированного объединения частей — `text | reasoning | tool-call | tool-result | file | image`. Роль `tool` перестаёт быть «почти assistant» и начинает означать ровно то, что означает.

## 3. Направление 1 — Компактирование контекста

### 3.1 Бюджет

```ts
interface ContextBudget {
  contextLength: number;   // из details.contextLength (уже есть в БД)
  maxOutput: number;       // generationSettings.maxOutputTokens
  reserve: number;         // 12–15% на системный блок и «дыхание»
  usable: number;          // contextLength - maxOutput - reserve
  compactAt: number;       // 0.75–0.8 * usable — порог компактирования
  hardStop: number;        // 0.95 * usable — аварийная редукция
}
```

`text_provider_model_details` уже содержит `contextLength` и `maxCompletionTokens` — брать оттуда, для моделей без данных использовать консервативный дефолт (например 32k) и настраиваемое переопределение в UI.

### 3.2 Подсчёт токенов

Трёхуровневая стратегия:

1. **Фактический usage** от провайдера после каждого шага (`streamText` → `result.usage`, `onStepFinish`) — записывать в `generation_run_steps.input_tokens/output_tokens` и агрегировать в `generation_runs`. Это истина в последней инстанции.
2. **Локальный токенизатор** для оценки *до* отправки: `gpt-tokenizer` для OpenAI-совместимых, tokenizer из `details.tokenizer` где известен. Кэшировать результат на `message_id + part_index` в таблице `message_token_counts` (пересчитывать только новые части).
3. **Эвристика** как fallback: для смеси русского и кода `ceil(chars / 3.2)` — намеренно пессимистичная оценка, лучше сжать раньше, чем упереться в лимит.

### 3.3 Лестница редукций

Компактирование через LLM — дорогая операция. До неё применяется дешёвая детерминированная лестница, в порядке возрастания потерь:

| Ступень | Что делает | Обратимо |
|---|---|---|
| R1. Обрезка tool-результатов | Правило на инструмент: `fs_read` — окно вокруг релевантного, `cmd_exec` — первые 100 + последние 50 строк, `grep` — топ-N совпадений. Вместо вырезанного — маркер `[…опущено 412 строк, доступно через read_tool_output(callId)…]` | Да (полный результат в БД) |
| R2. Дедупликация чтений | Файл прочитан 3 раза — в контексте остаётся последняя версия, предыдущие сворачиваются в ссылку | Да |
| R3. Схлопывание неудач | Серия упавших команд → одна строка «5 попыток запуска сборки завершились ошибкой TS2345 в src/x.ts» | Да |
| R4. Отбрасывание reasoning | Reasoning-части старых шагов удаляются из контекста | Да |
| R5. Summary-компактирование | LLM-сжатие диапазона сообщений | Да (см. ниже) |
| R6. Аварийное усечение | Сброс всего кроме системы, плана и последнего сообщения | Да |

### 3.4 Summary-компактирование

Механика по образцу автоматического компактирования Anthropic ([cookbook](https://platform.claude.com/cookbook/tool-use-automatic-context-compaction)): при превышении порога рабочий цикл приостанавливается **перед следующим вызовом модели**, генерируется структурированная сводка, диапазон сообщений заменяется одним сообщением со сводкой, цикл продолжается.

Отличия нашей реализации от эталона:

- **Ничего не удаляется.** Новая таблица:
  ```sql
  CREATE TABLE context_segments (
    id TEXT PRIMARY KEY,
    conversation_id TEXT NOT NULL REFERENCES chat_conversations(id) ON DELETE CASCADE,
    from_message_id TEXT NOT NULL,
    to_message_id TEXT NOT NULL,
    summary_json TEXT NOT NULL,
    model_id TEXT,
    tokens_before INTEGER NOT NULL,
    tokens_after INTEGER NOT NULL,
    reason TEXT NOT NULL CHECK(reason IN ('threshold','overflow','manual','model_switch')),
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
  );
  ```
  В UI сегмент рисуется свёрнутым блоком «сжато 24 сообщения · 51k → 4k токенов» с раскрытием оригинала. Это закрывает пункт 9 TODO («версионируемые summary без удаления исходных сообщений»).
- **Модель для сводки настраивается отдельно** (роль `summarizer` в ModelChain) — можно локальную Ollama, чтобы не тратить платный лимит.
- **Фиксированная структура сводки** — не свободный пересказ, а заполнение разделов:
  ```
  ## Задача
  ## Принятые решения (и почему)
  ## Изменённые файлы            ← пути + суть правки, обязательно
  ## Что уже проверено           ← прошедшие тесты, подтверждённые гипотезы
  ## Тупики                      ← что пробовали и почему не сработало
  ## Открытые вопросы
  ## Следующие шаги
  ```
  Раздел «Тупики» критичен: без него агент после компактирования заново повторяет уже провалившиеся попытки.

### 3.5 Инварианты (обязательны к покрытию тестами)

1. Никогда не разрывать пару `tool-call` / `tool-result` — провайдер отвергнет запрос.
2. Всегда сохранять целиком: системный блок, инструкции проекта, последнее сообщение пользователя, активный план задачи (`task_plans`), результаты незавершённых инструментов.
3. После компактирования расчётный размер контекста строго меньше `compactAt`, иначе — эскалация на следующую ступень.
4. Сообщения, попавшие в `context_segments`, не компактируются повторно (сводка сводок — только при явной эскалации, с пометкой уровня).
5. Компактирование происходит **на границе шага**, никогда — в середине стрима.

### 3.6 Ручное управление

- `/compact [фокус]` — сжать сейчас, опционально с указанием, что важно сохранить.
- Кнопка «сжать» + индикатор заполнения контекста в GUI (полоса: использовано / порог / лимит).
- Настройка порога на уровне проекта и агента.

## 4. Направление 2 — Хот-свитчинг моделей

Выбранное поведение: **авто при ошибке провайдера + авто при переполнении контекста**. Ручное переключение делается тем же механизмом и получается бесплатно.

### 4.1 ModelChain

Новая сущность — упорядоченный профиль моделей с ролями:

```ts
interface ModelChain {
  id: string;
  name: string;
  primary: string;              // modelId
  fallbacks: string[];          // по порядку
  summarizer: string | null;    // для компактирования
  policy: {
    retriesPerModel: number;    // 2
    backoffMs: number;          // 500, экспоненциально
    degradeCooldownMs: number;  // 300_000 — провайдер помечен «нездоров»
    requireTools: boolean;      // не переключаться на модель без tool-calling
  };
}
```

Привязка: проект → агент → чат (переопределение вниз по цепочке).

### 4.2 ResilientModel

Во встроенном виде фолбэка в AI SDK нет — это открытый запрос ([vercel/ai#9950](https://github.com/vercel/ai/issues/9950), [discussion #3387](https://github.com/vercel/ai/discussions/3387)); сообщество использует стороннюю обёртку `ai-fallback`. Делаем свою: обёртку над `LanguageModelV2`, которую возвращает `ProviderRegistry.resolve()`. RunEngine о переключении не знает — он просто получает модель, которая не падает.

Границы ответственности:
- `ResilientModel` — сетевые сбои, лимиты, недоступность. Прозрачный ретрай, переключение **на границе шага**.
- `RunEngine` — переполнение контекста: сначала компактирование, потом (если не помогло) запрос модели с бо́льшим окном из цепочки.

### 4.3 Классификация ошибок → действие

| Класс | Признаки | Действие |
|---|---|---|
| Транзиентная сеть | ECONNRESET, ETIMEDOUT, 502/503/504 | Ретрай той же моделью (backoff), после N — следующая |
| Лимит | 429, `limitRemaining ≈ 0` в `text_provider_configs.limits` | Сразу следующая, провайдер `degraded` на cooldown |
| Авторизация | 401/403, секрет отозван | Следующая, уведомление пользователю, провайдер помечен |
| Переполнение контекста | `context_length_exceeded`, `finishReason: "length"` на входе | Компактирование → повтор → при повторе модель с бо́льшим окном |
| Обрыв стрима | Стрим прервался с частичным текстом | Частичный текст фиксируется в журнале, следующая модель получает его как «продолжи с этого места» |
| Отказ по содержанию | Модерация провайдера | **Не переключать автоматически** — показать пользователю, предложить выбор |
| Ошибка инструмента | Инструмент упал | Не относится к модели, обрабатывается циклом инструментов |

### 4.4 Переключение без потери контекста

Работает за счёт журнала (§2.2). При смене модели контекст пересобирается заново:

- Пересчитывается бюджет под новое окно; при необходимости запускается компактирование.
- Нормализуются возможности: нет tool-calling — деградация в текстовый режим с явным предупреждением и отказом продолжать агентный ран; нет reasoning — reasoning-части выбрасываются; иной формат tool-результатов — перепаковка на уровне провайдера AI SDK.
- **Побочные эффекты не дублируются**: уже выполненные инструменты лежат в журнале с результатами, повторно не вызываются. Переключение всегда на границе шага, никогда — между вызовом инструмента и записью его результата.

### 4.5 Наблюдаемость

Новый тип события в `RunEvent`:

```ts
| { type: "run.model.switched"; runId: string; from: string; to: string;
    reason: "provider_error" | "rate_limit" | "context_overflow" | "manual";
    detail: string }
```

В UI — компактный бейдж внутри сообщения («⇄ mistral-large → qwen2.5-coder: лимит провайдера»). В `generation_runs` добавить `model_switches_json` для истории рана.

Проактивность: `text_provider_configs.limits` и `checked_at` уже пишутся — использовать, чтобы не *начинать* ран на модели с исчерпанным лимитом.

## 5. Направление 3 — CLI

Целевая модель: CLI как самостоятельное дополнение к приложению (по образцу пары «приложение Claude / Claude Code»), с общим ядром.

### 5.1 Состав

```
zvs                          интерактивный TUI (Ink)
zvs -p "почини тесты"        headless, один проход, вывод в stdout
zvs -p "..." --json          машинный вывод для пайплайнов
zvs run --stream-json        поток событий (те же RunEvent)
zvs --project my-app         выбор проекта
zvs --agent coder --model-chain fast
zvs --permission-mode ask|acceptEdits|plan|deny
zvs --allowed-tools fs_read,fs_edit,cmd_exec
zvs diff | undo | compact | cost | doctor
```

Коды возврата: `0` — успех, `1` — ошибка выполнения, `2` — отказано политикой, `3` — требуется одобрение в неинтерактивном режиме.

### 5.2 Совместный доступ к состоянию

Общая SQLite-база (`ZVS_HOME`, по умолчанию каталог userData приложения). Схема доступа:

1. CLI при старте проверяет, запущено ли приложение (lock-файл + именованный канал Windows / unix-socket).
2. **Запущено** → CLI подключается к хосту и выполняет ран там, получая обратно поток `RunEvent`. Один писатель в БД, никаких гонок, ран виден в GUI в реальном времени.
3. **Не запущено** → CLI поднимает ядро сам, становится писателем, берёт lock. WAL + `busy_timeout` как страховка.

Это же даёт бесплатный бонус: `zvs` из терминала внутри проекта продолжает тот же диалог, что открыт в GUI.

### 5.3 Общие слэш-команды

`/model`, `/compact`, `/project`, `/agent`, `/skills`, `/tools`, `/diff`, `/undo`, `/cost`, `/memory`, `/init` — реализуются **в ядре** как команды с описанием и схемой аргументов. CLI рендерит их в TUI, GUI — в композере чата. Одна реализация, два интерфейса.

### 5.4 Одобрения вне GUI

Существующая инфраструктура (`command_approval_requests`, риск `read/write/destructive`) переиспользуется. В TUI — интерактивный запрос. В headless — режим разрешений:

- `plan` — только чтение и рассуждение, никаких записей (режим по умолчанию для CI);
- `ask` — при запросе на запись ран останавливается с кодом `3` и печатает, что именно требовалось;
- `acceptEdits` — правки файлов внутри `directory_policy` без вопросов, команды — по-прежнему по политике терминала;
- `deny` — жёсткий отказ.

### 5.5 Технические оговорки

- `better-sqlite3` — нативный модуль. Для CLI нужна сборка под обычный Node, а не под Electron ABI; в приложении используется `electron-rebuild`. Решение: prebuild-артефакты для обоих ABI либо переход на `node:sqlite` (Node 26 в `engines` — доступен) для CLI-пути.
- Windows — основная платформа: именованные каналы, UNC-пути, регистр в путях, длина пути > 260 символов. Заложить в тесты политики путей с самого начала.

## 6. Направление 4 — Проекты

Трактовка: проект — контейнер, «чат на максималках», а не просто путь к папке. Один проект — много диалогов, общая настройка, общее знание, общая память.

### 6.1 Сущность

```sql
CREATE TABLE projects (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  root_path TEXT,                        -- NULL допустим: проект без кода
  instructions TEXT NOT NULL DEFAULT '', -- инструкции, заданные в UI
  instructions_file TEXT,                -- обнаруженный AGENTS.md / ZVS.md
  model_chain_id TEXT REFERENCES model_chains(id) ON DELETE SET NULL,
  default_agent_id TEXT REFERENCES automation_agents(id) ON DELETE SET NULL,
  directory_policy_id TEXT,
  terminal_policy_id TEXT,
  compact_threshold REAL NOT NULL DEFAULT 0.78,
  archived INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Плюс связи: `project_tools`, `project_skills`, `project_vector_stores`, и колонки `project_id` в `chat_conversations`, `memory_entries`, `task_plans`.

### 6.2 Наследование политик

Сейчас `directory_policy` и `terminal_policy` — синглтоны (`GLOBAL_ENTITY_IDS`). Их нужно сделать множественными с цепочкой разрешения:

```
глобальная политика ∩ политика проекта ∩ политика агента = эффективные права
```

**Строго пересечение, никогда не объединение.** Проект не может расширить права сверх глобальных — это фундаментальное свойство, без которого «открыть проект» становится эскалацией привилегий. Разрешение прав вычисляется один раз на старте рана и передаётся в инструменты как неизменяемый объект.

### 6.3 Инструкции проекта

- Автоподхват `AGENTS.md` (и/или `ZVS.md`) из корня проекта, с наблюдением за файлом и перечитыванием при изменении.
- Иерархия: файл в подкаталоге дополняет корневой при работе в этом подкаталоге.
- Проектные скиллы: `.zvs/skills/<name>/SKILL.md` — склеиваются с глобальными в `skillCatalog()`.
- Команда `/init` — сгенерировать `AGENTS.md`, изучив репозиторий (структура, команды сборки/тестов, соглашения).

### 6.4 Знание о репозитории

- **Карта репозитория**: дерево + экспортируемые сигнатуры, строится инкрементально на Rust-стороне, кэшируется по хэшу дерева, подаётся в системный блок в сжатом виде (сотни токенов, не тысячи).
- **Векторный индекс кода**: отдельное хранилище LanceDB на проект, разбиение по синтаксическим границам, а не по фиксированным окнам символов; инвалидация по mtime.
- **Память проекта**: типизация (`fact`/`preference`/`instruction`/`episode`) и поиск через FTS5 (`memory_search`) **уже реализованы** — из пункта 9 TODO остаётся только добавить `memory_entries.project_id` и разделение областей видимости. Векторный поиск по памяти — позднее, сменным адаптером.

### 6.5 Git-осведомлённость

- Текущая ветка, состояние рабочего дерева, diff относительно базы — в системный блок (компактно, без содержимого).
- **Чекпоинты**: перед каждой серией правок снимок изменяемых файлов в `.zvs/checkpoints/<runId>/`. Это работает и вне git, и не мешает индексу git — важно, потому что агент не должен трогать staging пользователя.
- `/undo` — откат к чекпоинту; `/diff` — просмотр всего, что изменил ран.

## 7. Направление 5 — то, что добавляю от себя

### 7.1 Файловые инструменты (P0, без них остальное бессмысленно)

| Инструмент | Назначение | Существенные детали |
|---|---|---|
| `fs_read` | Чтение с `offset`/`limit` | Нумерация строк, определение кодировки, отказ на бинарных, лимит на размер ответа |
| `fs_list` | Листинг дерева | Уважает `.gitignore`, ограничение глубины |
| `fs_write` | Создание/полная перезапись | Только для новых файлов или после явного чтения |
| `fs_edit` | Точечная замена фрагмента | Требует уникальности фрагмента; неуникальный → ошибка с показом всех совпадений |
| `fs_multi_edit` | Пакет правок одного файла | Атомарно: либо все, либо ни одной |
| `fs_apply_patch` | Применение unified diff | Для крупных правок дешевле по токенам, чем `fs_write` |
| `fs_move` / `fs_delete` | Перемещение/удаление | Удаление — в корзину проекта, не безвозвратно |

Сквозные правила:

1. **Read-before-edit.** Нельзя редактировать файл, не прочитанный в этом ране. Отсекает галлюцинации содержимого.
2. **Проверка mtime.** Файл изменился с момента чтения — правка отклоняется с требованием перечитать. Защита от затирания правок пользователя.
3. **Атомарная запись.** Временный файл + `rename`, сохранение оригинального окончания строк (CRLF/LF) и BOM — критично на Windows.
4. **Все пути — через `DirectoryPolicy`.** Права `read`/`create`/`modify`/`delete`/`execute` в гранте уже описаны в `directory-policy.dto.ts`, но сегодня проверять их нечему — файловых инструментов нет. Нужен единый `PathResolver`: нормализация, запрет обхода вверх, разрешение симлинков **до** проверки, отдельная обработка UNC-путей, сопоставление прав с операцией.
5. **Возврат — дифф, не содержимое.** `fs_edit` отвечает диффом изменения, а не полным файлом: экономия токенов и одновременно основа для UI-ревью.
6. **Чекпоинт перед первой правкой файла в ране.**

### 7.2 Ревью и откат

Diff-viewer в GUI (панель изменений рана), `/diff` и `/undo` в CLI, режим `acceptEdits`. Риски `write`/`destructive` в `generation_tool_calls` уже предусмотрены схемой — переиспользуются как есть.

### 7.3 Обратная связь от кода

Инструмент `project_check` — запуск заданных в проекте команд (`typecheck`, `test`, `lint`, `build`) с **нормализацией вывода** в единый формат `файл:строка:колонка: сообщение` и агрессивной обрезкой. Без нормализации вывод `tsc -b` или `vitest` съедает контекст быстрее, чем что-либо ещё в системе.

Позднее — LSP-клиент для диагностик без запуска сборки (отдельный этап, ощутимо дороже).

### 7.4 Подагенты

`task_spawn` — запуск изолированного подагента с собственным контекстом и бюджетом для задач вида «найди, где реализована авторизация» или «изучи, как устроен модуль X». В родительский контекст возвращается **только итоговый ответ**, а не десятки прочитанных файлов.

По экономии контекста это вторая по силе мера после компактирования, а инфраструктура (агенты, политики, реестр инструментов) уже есть — нужен только механизм вложенного рана и передача урезанного набора прав вниз (подагент не может получить больше прав, чем родитель).

### 7.5 MCP

Пункт 10 TODO. Реализуется как внешний адаптер `ToolRegistry` без изменения внутреннего контракта инструментов, с отдельными разрешениями и политикой одобрений на каждый сервер и каждый инструмент. Логично делать **после** проектов: MCP-серверы естественно конфигурируются на уровне проекта.

### 7.6 Стоимость и наблюдаемость

`details.promptPrice` / `completionPrice` уже есть в БД. После включения учёта usage (§3.2) получаем: стоимость рана и диалога, `/cost`, предупреждение о дорогой операции, выбор модели с учётом цены в ModelChain.

### 7.7 Тесты (Vitest уже настроен)

Обязательный минимум, без которого этапы не считаются закрытыми:

- **Сборка контекста** — снапшот-тесты `Journal → ModelMessage[]` для каждого режима.
- **Компактирование** — инварианты §3.5, особенно целостность пар tool-call/tool-result и соблюдение бюджета.
- **Fallback** — мок-провайдер, воспроизводящий каждый класс ошибок из §4.3; проверка отсутствия повторного выполнения инструментов.
- **Политика путей** — обход вверх, симлинки, UNC, регистр, длинные пути, кириллица в путях.
- **Файловые инструменты** — атомарность, сохранение CRLF/BOM, конфликт по mtime, идемпотентность `apply_patch`.

## 8. Дорожная карта

Порядок продиктован зависимостями, а не важностью.

### Этап 0 — Фундамент

Журнал сообщений в частях; расширение `content_json`; миграция существующих данных; сборка контекста из журнала с включением tool-call/tool-result; учёт usage в `generation_run_steps` и `generation_runs`; токенизатор и кэш подсчётов; `ContextBudget`; индикатор заполнения контекста в UI.

*Затрагивает:* `run-engine.ts`, `chat.repository.ts`, `baseline-schema.ts` + миграция, `shared/models/chat.ts`, `ChatStore.ts`.
*Критерий готовности:* агент видит результаты своих инструментов на следующем шаге; в UI виден расход токенов.

### Этап 1 — Файловые инструменты

Порты `FileSystemPort`; инструменты §7.1; чекпоинты; diff-viewer; `/diff`, `/undo`; read-before-edit и проверка mtime; расширение `DirectoryPolicy` правами `read`/`write`/`delete`.

*Критерий:* агент правит код в рамках политики, любую правку видно диффом и можно откатить.

### Этап 2 — Компактирование

Лестница редукций R1–R6; `context_segments`; сводка по фиксированной структуре; роль `summarizer`; `/compact`; свёрнутый блок сжатия в UI.

*Критерий:* сессия на 500k токенов работы укладывается в модель с окном 32k без потери сути.

### Этап 3 — Хот-свитчинг

`model_chains`; `ResilientModel`; классификатор ошибок; интеграция с компактированием при переполнении; событие `run.model.switched`; UI цепочки моделей.

*Критерий:* отключение основного провайдера посреди агентного рана не роняет ран и не выполняет инструменты повторно.

### Этап 4 — Проекты

`projects` и связи; `project_id` в диалогах, памяти, планах; мультизаписные политики с наследованием-пересечением; `AGENTS.md`; проектные скиллы; карта репозитория; индекс кода; git-осведомлённость; UI проектов.

*Критерий:* переключение проекта меняет права, знания, память и модельную цепочку одним действием.

### Этап 5 — Ядро и CLI

Выделение `packages/core`; порты; `packages/cli` (сначала headless, затем TUI); мост к запущенному приложению; общие слэш-команды; режимы разрешений; решение вопроса с ABI `better-sqlite3`.

*Критерий:* `zvs -p "..."` работает и с запущенным приложением, и без него, с теми же политиками.

### Этап 6 — Усиление

Подагенты; `project_check`; MCP-адаптер; LSP-диагностика; LangGraph для долгоживущих сценариев (пункт 10 TODO).

### Замечание о порядке

Выделение ядра (этап 5) стоит **после** этапов 0–4 намеренно: рефакторинг границ дешевле, когда доменные типы устоялись. Но порты (`FileSystemPort`, `ProcessPort`, `ApprovalPort`) вводятся **сразу на этапе 1** — тогда вынос ядра становится механическим перемещением файлов, а не переписыванием.

## 9. Риски

| Риск | Оценка | Смягчение |
|---|---|---|
| Миграция `content_json` ломает существующие диалоги | Высокий | Версия схемы, миграция вперёд-совместимая (старый формат читается как одна text-часть), резервная копия БД перед миграцией |
| Агент портит файлы пользователя | Высокий | Чекпоинты до этапа выдачи прав на запись; `acceptEdits` не по умолчанию; политика пересечением |
| Сводка теряет критичное | Средний | Фиксированная структура с разделом «Тупики»; исходники сохраняются; ручной `/compact` с фокусом |
| Расхождение GUI и CLI | Средний | Единственная реализация в ядре; общие слэш-команды; общий набор тестов |
| ABI `better-sqlite3` для CLI | Средний | Prebuild под оба ABI либо `node:sqlite` для CLI |
| Конкурентная запись в БД | Средний | Один писатель + мост к приложению; WAL и `busy_timeout` как страховка |
| Windows-специфика путей | Средний | Тесты политики путей с первого этапа |
| Разрастание объёма работ | Высокий | Этапы 0–2 самодостаточны и дают ценность сами по себе; 3–6 можно двигать по срокам |

## 10. Что менять в первую очередь — конкретно

Если начинать завтра, минимальный связный срез — этапы 0 и 1:

1. `shared/models/chat.ts` — типы частей сообщения (`text | reasoning | tool-call | tool-result | file`).
2. `baseline-schema.ts` + миграция — расширенный `content_json`, `message_token_counts`.
3. `chat.repository.ts` — `journalMessages(conversationId)` вместо `historyMessages(...)`; запись частей вместо текста.
4. `run-engine.ts` — `ContextBuilder` вместо inline-`.map()`; чтение `usage` в `onStepFinish`; запись токенов.
5. `tool.registry.ts` — семь новых файловых инструментов + порт файловой системы.
6. Новый `host/infrastructure/filesystem/checkpoint.service.ts`.
7. Новый `core/policy/path-resolver.ts` — единая проверка пути и права под операцию (права в гранте уже есть, применять их некому).
8. UI: индикатор контекста в композере, панель диффов рана.
