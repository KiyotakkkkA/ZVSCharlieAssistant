# ADR-0002. Доставка обновлений desktop-клиента

- **Статус:** Proposed — требует вашего решения перед реализацией
- **Дата:** 2026-09-02
- **Затрагивает:** сборка `desktop`, инфраструктура `docker/caddy`,
  будущая страница changelog в `ZVSMain/frontend`

## Контекст

Сейчас `zvs-desktop` собирается через `electron-vite build` и не имеет ни
установщика, ни канала обновлений: новая версия до пользователя не доедет.
Нужно закрыть три связанные задачи:

1. **Хранилище артефактов** — где лежат установщики и манифест версий.
2. **Автообновление** — как клиент узнаёт о новой версии и ставит её.
3. **Changelog** — что пользователь читает перед установкой.

Ограничения, важные для выбора:

- Инфраструктура уже своя: Caddy с TLS, домены `*.zvsd.ru`, docker compose.
- Основная платформа — Windows; macOS/Linux желательны, но позже.
- Пользователи будут внешние: канал обновлений становится **каналом
  выполнения кода на чужой машине**. Это главный риск всего ADR.
- Ассистент работает в фоне (трей, сценарии) — обновление не должно
  прерывать выполняющийся сценарий.

## Решение

### 1. Хранилище: self-hosted `dl.zvsd.ru`

Отдельный виртуальный хост Caddy, раздающий статику из тома:

```
dl.zvsd.ru/desktop/stable/
  latest.yml                       # манифест electron-updater (Windows)
  ZVS-Assistant-Setup-1.2.0.exe
  ZVS-Assistant-Setup-1.2.0.exe.blockmap
  RELEASES.json                    # наш changelog-фид
```

Причина: артефакты остаются в том же периметре доверия, что и ZVS ID,
домен и TLS уже есть, никакой внешней зависимости в критическом пути.
Каналы разделяются директорией (`stable/`, `beta/`), а не хостом.

### 2. Автообновление: `electron-updater`, provider `generic`

```ts
autoUpdater.setFeedURL({
  provider: "generic",
  url: "https://dl.zvsd.ru/desktop/stable",
});
```

Политика:

- Проверка при старте и далее раз в 6 часов.
- Скачивание — фоновое; **установка только по явному согласию** и только
  когда нет активных сценариев (`ScenarioRuntimeEngine` знает об этом).
- В трее и в «О приложении» — состояние: «актуально» / «скачивается» /
  «готово к установке».

### 3. Подпись — обязательное условие

`electron-updater` проверяет подпись установщика на Windows. **Без
code signing автообновление включать нельзя:** канал раздачи становится
готовым механизмом доставки произвольного кода — достаточно один раз
подменить файл на диске или перехватить соединение.

Минимум: сертификат Authenticode (OV или EV) и подпись в CI. До этого —
только ручная загрузка с `dl.zvsd.ru`, где пользователь сам решает.

### 4. Changelog: один источник, две витрины

Записи живут в репозитории (`desktop/CHANGELOG.md`, формат
[Keep a Changelog](https://keepachangelog.com)). Сборка конвертирует их в
`RELEASES.json`:

```json
{
  "version": "1.2.0",
  "date": "2026-09-02",
  "channel": "stable",
  "notes": { "added": ["…"], "fixed": ["…"], "changed": ["…"] }
}
```

Его читают:

- страница `hub.zvsd.ru/library/zvs-assistant/changelog` — публичная история;
- модальное окно «Что нового» в самом клиенте после обновления.

Один источник — не разъедется.

## Последствия

**Хорошо**

- Полный контроль над каналом: свои версии, откаты, доля раскатки.
- Нет зависимости от доступности и правил стороннего сервиса.
- Changelog пишется один раз и попадает и в веб, и в приложение.

**Плохо / за что платим**

- Трафик установщиков идёт на ваш сервер: ~100 МБ на клиента за релиз.
  При росте аудитории потребуется CDN перед `dl.zvsd.ru`.
- Нужен пайплайн публикации и дисциплина «не трогать руками» директорию
  релизов.
- Code signing — это деньги (EV-сертификат) и возня с хранением ключа в CI.
- Резервные копии артефактов теперь наша забота: удалённый по ошибке
  `latest.yml` останавливает обновления у всех.

**Открытые вопросы**

- Нужен ли канал `beta` сразу или после первого стабильного релиза?
- Дельта-обновления (blockmap) — включать сразу или после замера трафика?
- Сколько прошлых версий держать для отката (предложение: 3)?

## Альтернативы

### GitHub Releases (`provider: "github"`)

Бесплатно, CDN из коробки, `electron-updater` поддерживает нативно,
подписанные теги дают дополнительную гарантию происхождения.

Отклонено: привязывает выпуск продукта к внешней платформе и (для приватного
репозитория) требует раздачи токена клиентам. Плюс доступность GitHub из РФ
нестабильна — для канала обновлений это критично.

### S3-совместимое хранилище (Yandex Object Storage / R2 / MinIO)

Лучше всего масштабируется и снимает трафик с приложения. Отклонено *на
сейчас* как преждевременное: добавляет бакет, ключи и ещё один участок
инфраструктуры до того, как появился первый пользователь. Это естественный
следующий шаг — `electron-updater` с provider `generic` переедет на S3
сменой одного URL, без изменения клиента.

### Squirrel.Windows напрямую / нативный MSI + WSUS

Отклонено: `electron-builder` уже умеет NSIS и Squirrel, а ручная работа с
ними не даёт ничего сверх, кроме поддержки.

### Без автообновления — только ручная загрузка

Отклонено как постоянное решение: пользователи остаются на старых версиях, и
исправление уязвимости до них не доезжает. Но это **корректное временное
состояние**, пока нет подписи кода, — и именно с него мы начинаем.

## План внедрения

| Шаг | Что                                                          | Блокирует         |
| --- | ------------------------------------------------------------ | ----------------- |
| 1   | `electron-builder`, NSIS-установщик, `CHANGELOG.md`          | —                 |
| 2   | `dl.zvsd.ru` в Caddy + том для артефактов                    | —                 |
| 3   | Скрипт публикации: сборка → подпись → выгрузка → `latest.yml` | сертификат        |
| 4   | `electron-updater` в main-процессе + UI состояния в трее      | шаг 3             |
| 5   | `RELEASES.json`, страница changelog, окно «Что нового»        | шаг 1             |
| 6   | Канал `beta` и постепенная раскатка                          | первый релиз      |

Шаги 1, 2 и 5 можно делать сразу — они не зависят от сертификата. Шаг 4
включаем **только** после шага 3.
