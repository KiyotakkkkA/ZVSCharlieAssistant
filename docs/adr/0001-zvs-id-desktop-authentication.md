# ADR-0001. Подключение ZVS ID в desktop-клиенте

- **Статус:** Accepted; часть про `zvsdesk://` отменена
  [ADR-0004](0004-drop-the-zvsdesk-scheme.md)
- **Дата:** 2026-09-02
- **Затрагивает:** `desktop/src/host/infrastructure/zvs-id/*`,
  `desktop/src/host/application/services/zvs-id.service.ts`,
  `desktop/src/host/infrastructure/electron/deep-link.controller.ts`,
  `ZVSMain/frontend/app/oauth/*`

## Контекст

Desktop-клиенту нужно действовать от имени пользователя ZVS ID: сейчас — чтобы
показать, кто вошёл, дальше — чтобы обращаться к сервисам экосистемы. Значит
нужен OAuth 2.0 / OpenID Connect поверх Zitadel, который стоит за ZVS ID.

Условия, которые формируют решение:

1. **Приложение — публичный клиент.** Установщик уезжает на чужую машину;
   любой секрет внутри него можно достать дизассемблером или просто из строк
   бинарника. Значит `client_secret` использовать нельзя ни в каком виде —
   аутентификация клиента невозможна в принципе.
2. **Пароль не должен проходить через приложение.** Если форма входа внутри
   Electron, то пользователь вводит пароль ZVS ID в окно, которое мы
   контролируем: ломается смысл единого входа, недоступны 2FA-потоки и
   будущие passkeys, а сам пароль оказывается в памяти нашего процесса.
3. **Нужен возврат управления в приложение.** Браузер должен как-то отдать
   код авторизации обратно в уже запущенный Electron-процесс.
4. **`zvsdesk://` нужен независимо от аутентификации** — для кнопок
   «Открыть» и «Подключить» в веб-библиотеке `hub.zvsd.ru/library`.

RFC 8252 (OAuth 2.0 for Native Apps) отвечает на пункты 1–3 прямо: только
внешний браузер, только authorization code + PKCE, redirect — на loopback,
на custom scheme или на claimed HTTPS URI.

## Решение

**Authorization Code + PKCE (S256) с redirect на loopback-интерфейс.**
`zvsdesk://` остаётся, но только как канал запуска приложения — не как
redirect URI.

Поток:

```
Electron (main)              системный браузер            ZVS ID
     |                              |                        |
 1.  |-- listen 127.0.0.1:0 ------->|                        |
 2.  |-- shell.openExternal ------->|                        |
     |                              |-- /oauth/authorize --->|
     |                              |   (наш экран согласия) |
     |                              |<-- 302 127.0.0.1/... --|
 3.  |<-- GET /callback?code&state -|                        |
 4.  |-- сверка state --------------|                        |
 5.  |-- POST /token + verifier ----------------------------->|
     |<-- access + refresh -----------------------------------|
 6.  |-- safeStorage.encryptString -> zvs-id.json             |
```

Существенные детали:

- **Порт всегда эфемерный** (`listen(0)`). Фиксированный порт — это и
  конфликт с другими приложениями, и подсказка атакующему, какой порт
  занять первым.
- **Слушаем строго `127.0.0.1`**, не `0.0.0.0`: иначе локальный сервер
  становится виден по сети.
- **`state` сверяется через `timingSafeEqual`.** Он защищает не от кражи
  кода, а от подсовывания *чужого* кода в нашу сессию (CSRF на redirect).
- **PKCE обязателен**, хотя redirect и так защищён: `code_verifier` не
  выходит за пределы процесса, поэтому перехваченный код бесполезен.
- **Сервер живёт ровно один запрос** и закрывается по таймауту 5 минут.
  Любой путь кроме `/callback` — 404.
- **Точка входа — `https://hub.zvsd.ru/oauth/authorize`, а не
  `authorization_endpoint` из discovery.** Параметры те же, но пользователь
  видит наш экран выбора аккаунта и согласия вместо формы Zitadel.
- **Токены шифруются через Electron `safeStorage`** (DPAPI на Windows,
  Keychain на macOS) в `userData/zvs-id.json`. Если ОС не даёт шифрование —
  UI показывает это явно, а не молчит.

## Последствия

**Хорошо**

- Пароль и второй фактор никогда не попадают в наш процесс.
- Код авторизации получает ровно тот процесс, который занял порт: ОС не
  отдаёт один и тот же порт двум процессам.
- Работает одинаково на Windows, macOS и Linux без платформенного кода.
- Утечка `zvs-id.json` без учётной записи ОС бесполезна.

**Плохо / за что платим**

- В Zitadel нужен отдельный native-клиент с разрешённым
  `http://127.0.0.1:*/callback` и auth method `none`.
- Персональные фаерволы иногда спрашивают про прослушивание порта — это
  видит пользователь, и это выглядит подозрительно.
- Нужен запасной путь, если порт занять не удалось (сейчас — понятная
  ошибка; при жалобах вернёмся к варианту с custom scheme).
- `refresh_token` лежит на диске: нужен явный «Отключить» с отзывом токена,
  и он реализован.

**Что теперь обязаны поддерживать**

- Ротацию refresh-токена (Zitadel может выдавать новый при каждом refresh).
- Совместимость формата `zvs-id.json` — при смене структуры читаем старую
  версию или заставляем войти заново, но не падаем.

## Альтернативы

### Custom scheme `zvsdesk://auth/callback` (путь VSCode)

Так VSCode подключает GitHub. Проще: не нужен локальный сервер, не ругается
фаервол, работает при жёстких сетевых политиках.

Отклонено: схема регистрируется **глобально в ОС**, и никакой арбитраж не
мешает другому приложению зарегистрировать `zvsdesk://` на себя. Тогда чужой
процесс получит код авторизации. PKCE спасает от обмена кода на токен, но
атакующий всё равно ломает вход пользователю и видит `state`. RFC 8252
§7.2 прямо рекомендует loopback как более надёжный вариант. Остаётся
кандидатом на fallback, если loopback окажется недоступен у реальных
пользователей.

### Device Authorization Grant (RFC 8628)

Пользователь вводит короткий код на `id.zvsd.ru/device`. Не нужен ни redirect,
ни локальный порт; отлично для headless и SSH-сценариев.

Отклонено сейчас: заметно хуже UX для настольного приложения с окном — код
приходится переносить руками. Сам грант в Zitadel уже включён (discovery
объявляет `urn:ietf:params:oauth:grant-type:device_code`), не хватает только
страницы на вебе. Вернёмся к этому, если появится серверный или консольный
режим.

### Встроенное окно `BrowserWindow` с формой входа

Отклонено: RFC 8252 §8.12 запрещает embedded user-agent. Приложение видит
всё, что вводит пользователь, ломается SSO с браузером, не работают
менеджеры паролей, а пользователь не может проверить адресную строку.

### Claimed HTTPS URI (App Links / Universal Links)

Самый защищённый вариант: ОС проверяет владение доменом. Отклонено:
на Windows для desktop-приложений полноценной поддержки нет, а именно
Windows — основная платформа клиента.
