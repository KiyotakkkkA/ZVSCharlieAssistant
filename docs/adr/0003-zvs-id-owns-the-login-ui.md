# ADR-0003. ZVS ID как login UI для Zitadel

- **Статус:** Accepted (ожидает применения на существующем инстансе)
- **Дата:** 2026-09-02
- **Затрагивает:** `ZVSMain/frontend/app/oauth/*`,
  `ZVSMain/backend/src/oauth/*`, `docker/docker-compose.*.yml`

## Контекст

Экран выбора аккаунта и согласия живёт у нас (`hub.zvsd.ru/oauth/*`), а токены
выпускает Zitadel. Связать эти две половины можно двумя способами.

Первая реализация делала это **проксированием**: бэкенд сам дёргал
`GET {issuer}/oauth/v2/authorize` с `redirect: manual` и выковыривал
идентификатор запроса из заголовка `Location`. Работает, но опирается на
недокументированную деталь — как именно Zitadel формирует редирект. Мы уже
были вынуждены принимать два имени параметра (`authRequest` и
`authRequestID`), потому что не знали заранее, какое придёт. Обновление
Zitadel может сломать все входы, и ни компилятор, ни тесты этого не поймают.

У Zitadel есть штатный механизм: instance feature `loginV2.baseUri`. Он
существует ровно для сценария «свой login UI» — Zitadel сам редиректит
пользователя на `{baseUri}login?authRequest=<id>`, а мы завершаем запрос через
Session API. Это контракт, а не догадка.

Осложнение: под `baseUri` Zitadel адресует не только вход. Туда же уходят
logout-подтверждение, device flow и callback'и внешних IdP. Забрать префикс
целиком — значит обязаться реализовать всё это.

## Решение

**Отдаём `loginV2.baseUri` на `https://hub.zvsd.ru/oauth/`, но обслуживаем
своими руками только вход.**

- `/oauth/login` — наш экран: выбор аккаунта, согласие, завершение auth request.
- `/oauth/authorize`, `/oauth/select_account` — прежние маршруты, оставлены
  как удобные точки входа и для прямых ссылок.
- `/oauth/[...zitadel]` — catch-all, который 307-редиректит любой
  неизвестный путь обратно в `https://id.zvsd.ru/ui/v2/login/…` с исходным
  query. Logout, device flow и IdP-callback'и продолжают обслуживаться
  контейнером `zitadel-login`.

Так мы получаем контракт на вход и не берём на себя обязательств по потокам,
которых у нас пока нет.

Проксирование через `startAuthRequest` **остаётся** — но только как
совместимость для прямых обращений на `/oauth/authorize?client_id=…`. Поломка
этого пути теперь стоит удобства, а не всех входов сразу.

## Последствия

**Хорошо**

- `authorization_endpoint` из discovery снова корректен: сторонние OIDC-
  библиотеки работают без специальных URL, инструкции упрощаются.
- Убран сетевой round-trip «бэкенд → Zitadel» на каждой авторизации.
- Первый вход в первопартийное приложение тоже стабильнее: редирект теперь
  ведёт на наш собственный URL-шаблон, который мы контролируем.

**Плохо / за что платим**

- Появился catch-all, о котором нужно помнить: любой новый маршрут под
  `/oauth/` перехватывает то, что раньше уходило в Zitadel.
- Если однажды понадобится device flow или внешний IdP, решение придётся
  пересматривать — либо реализовывать эти экраны у себя, либо оставлять их
  Zitadel навсегда.
- **Консоль Zitadel начинает зависеть от нашего фронтенда.** С
  `loginV2.required: true` через наш экран идут все входы, включая вход
  администратора в саму консоль. Если фронтенд или бэкенд лежат, в консоль
  не зайти — а чтобы откатить настройку, обычно нужна консоль. Круг
  разрывается сервисным аккаунтом: `npm run zitadel:set-login-ui` ходит по
  JWT-ассершену, без браузера, поэтому откат возможен и при мёртвом
  фронтенде. Это единственный аварийный выход, и он должен оставаться
  рабочим — ключ сервисного аккаунта нельзя терять.
- Настройка живёт в базе инстанса, а не в compose, и переключать её нужно
  **после** того, как бэкенд поднят и хотя бы один аккаунт заведён. Compose
  намеренно оставлен на UI Zitadel: если свежий инстанс сразу поднять с нашим
  baseUri, первый вход в консоль пойдёт на ещё не запущенный фронтенд и
  установка встанет.

## Применение к существующему инстансу

Переключение — отдельный шаг после установки, а не часть первого запуска.
Предусловия: бэкенд и фронтенд подняты, вход на `hub.zvsd.ru` работает,
у сервисного аккаунта есть роль **IAM_OWNER**.

```bash
cd backend
npm run zitadel:set-login-ui -- https://hub.zvsd.ru/oauth/
```

Роль выдаётся в консоли: Instance Settings → Managers → «+». Откат — тот же
скрипт с `https://id.zvsd.ru/ui/v2/login/`; он работает и когда фронтенд
недоступен, потому что аутентифицируется ключом сервисного аккаунта.

## Отдельно: два пути аутентификации

Первопартийный фронтенд входит через `/auth/login` и получает токены напрямую,
не проходя через `/oauth/authorize`. Это **осознанный срез**, а не недосмотр:

- форма ввода пароля всё равно одна и та же — `/login`;
- сессия Zitadel создаётся одним и тем же кодом (`startPasswordSession`);
- экран согласия для собственного приложения бессмысленен.

Цена — `BrowserAccount` заполняется в двух местах и о первопартийном пути надо
помнить отдельно. Полный переход на «сам себе OAuth-клиент» дал бы один путь
вместо двух, но переписывает вход, 2FA и восстановление пароля ради
архитектурной чистоты. Возвращаемся к этому, когда появятся passkeys —
там единый путь начнёт окупаться.

## Альтернативы

### Оставить проксирование

Ноль изменений, работает сегодня. Отклонено: держит критический путь на
недокументированном поведении стороннего сервиса.

### Забрать `baseUri` целиком и реализовать все экраны

Максимальный контроль над UX. Отклонено сейчас: logout, device flow и IdP —
это отдельные экраны, которых у нас нет, а Zitadel их уже умеет.
